# 実運用バックエンド設計案：公開決定・私的会計・銀行強制

版：0.1、承認待ち。対象：指摘1〜3の実運用接続と、それに不可欠な認証・資格・保存・外部連携。ユーザーはデモ配備を選ばず、バックエンドの設計を先に進めると選択した。

参照仕様：[v0.4](2026-10-09-action-requirements-design.md)。そのU-01〜05は既決定、人数・期限・計算方法・技術選択は引き続き未承認案。本書は補助設計であり、v0.4を書き換えず、数値承認やG-01〜05解除をしない。[アプリ操作デモ](../../reviews/2026-10-14-app-workflows.md)の137件成功を、外部銀行・合意基盤の能力検証に読み替えない。

## 1. 最重要の判断

**一般的なWeb DB＋outbox＋決済APIだけでは、要求する実運用の安全性は成立しない。** DBで最新条件を読んだ後に候補が失効し、その後に銀行が不可逆確定するTOCTOUが残る。Saga補償は送金の未実行を保証しない。一般的なPSPの冪等キーは権利の最新性、旧版の永久失効、版横断総額、手動経路の強制を保証しない。

実受付の前提は、既存の外部決済/保管主体が、権利更新・失効・予約・実行版・不可逆銀行commitを共同の順序に参加させ、全経路で条件を強制できること。そのプロトコル、責任、署名証拠、接続検証が成立しない事業者は採用不可。本書は事業者がその能力を持つと断定しない（参照仕様PAY-08、第13.2節、G-03）。

## 2. 推奨する論理構成

参照仕様の構成A（既存の検証可能な合意基盤＋分離した外部サービス）を設計候補として維持する。独自チェーン・投票トークン・USDC金庫を追加しない。物理DB/合意基盤/外部事業者/暗号方式は未選定。

```text
利用者端末 ── 公開項目・目的別の署名操作 ── API/リレイヤー
   │                                         │
   │                                         ├─ 検証・認可・ゲート照合
   │                                         ├─ 合意基盤 → 最終公開決定/カタログ
   │                                         └─ 既存外部保管の条件強制 → 私的権利/銀行commit
   ├─ 端末内AI ← 検証済み公開カタログ・モデル   │
   ├─ 本人情報 → 外部資格/所持結合担当         └─ 証明検証後の投影・操作照会
   ├─ 決済/口座 → 外部決済/保管主体
   ├─ 証拠原本/正式委任 → 選任弁護士の直接受付
   └─ 任意通知メール → 分離した通知領域 → 契約適合する配信主体
```

### 正本と投影

| 領域 | 権威ある正本・確定主体 | アプリ側の役割 |
|---|---|---|
| 公開案件、審査、選任、承認、GateDecision | 未選定の検証可能な合意基盤。適格な本人/既存パネルの署名を検証 | 依頼の中継、証明検証、公開投影・独立ミラー。DB編集を承認にしない |
| 入金因果版、本人集約権利、予約、現金、銀行実行 | 参照仕様の既存外部決済/保管主体と条件強制エンジン | 最小証明の検証、隔離された会計照会/投影。推定残高で送金しない |
| 銀行と公開決定/外部失効の共同順序 | 事業者が保証する共同整合プロトコル（未証明） | 証明なしでは実行依頼を止める。自前DBロックで代替しない |
| アカウント/鍵/セッションepoch | AUTHに従う認証領域 | 毎回失効・epoch検証。資格・票・入金所持とは別 |
| メール購読/抑止/配送終端 | 通知専用領域＋独立抑止記録＋事業者確定点 | 確定した公開更新だけ通知。会計/投票への結合表なし |

Firestoreを使う場合も、当初の候補用途は索引・証明付き投影・耐久inbox/outbox・ローカル整合検査。トランザクションはそのDB内の保証に留まる。既存`auth-security`用途のDB/サービス権限を業務台帳へ流用しない。単独運用者が外部正本を上書きできる構成は不採用。

合意正本に置くのは許可済み提案の版/条件hash/決定/参照/catalog版の検証記録であり、提案・カタログ本文をチェーン等へ永久保存しない。本文/索引は訂正・削除可能な配信領域へ置き、提案の審査通過前は公開ミラーへ複製しない。禁止個人情報のhashを公開正本へ入れて匿名化と呼ばない。

配信bundleの案はcatalogVersion、environment/schema/rule、本文/索引hash、対応FinalDecision/最終性ref、署名鍵版を真正に結合する。端末/独立ミラーは承認鍵・版・署名・内容hash・最終性を検証する。形式/暗号方式は未採用で、配信署名だけで案件同一性やFINALを成立させない。

新たな裁定権・銀行例外権を持つ主体は追加しない。下記のportは参照仕様の既存の主体を実装上分離したインターフェースである。

## 3. 個人情報・鍵・役割

### 3.1 保管を分ける

| 保管領域 | 許容する情報 | 禁止する結合/権限 |
|---|---|---|
| Auth | ランダムID、パスキー公開鍵、失効、epoch、目的別challenge | 投票秘密/本人資料/入金本人対応表を持たない |
| Notifications | email、公開購読対象、確認/同意、subscriberId/generation、最小配送記録 | auth ID、投票秘密、privateReceiptRef/privateRefundOwnerRefへの対応表なし |
| Public decisions | 公開提案/職業情報の許可済み範囲、集合commitment、審査結論、選任、合計/決定証明 | 個別票の本人原票、個別金額、メール/資料ハッシュを公開しない |
| Isolated accounting projection | 募集/使途、私的ランダムref、JPY状態別額、権利/取引版、最小署名証明 | 個人金額/時刻/refを公開せず、本人照会ID・口座/カード・生Webhookを持たない |
| Provider/qualified professional（サービス外） | 本人資料、本人と入金の結合、銀行受取先、証拠/正式委任 | 運営の通常/管理/サポート/復旧/権限昇格から取得できない契約・技術権限 |

通知メールは収集するが任意であり、通知を選ばない人の閲覧/投票を制限しない。メールログインは決定していない。パスキーも初期提案で、ログイン鍵と投票資格の秘密を分離する。二つのDBへ分けただけで完全匿名とはしない（U-01〜05、AUTH、ID-01〜07、MAIL-03）。

既定のWebhookにPIIが含まれる場合、アプリへ受信してから削る方式を通常の接続契約にしない。事業者側でプライバシー最小化した署名証明を返せることを要求する。誤送信/悪意ある入力の完全な受信ゼロは保証せず、閉じたschemaで拒否し、ログ・永続化・公開へ拡散させない。

### 3.2 権限

- 共有Basicは検証環境の入口だけ。本人、参加条件、1人1票、パネル独立性、入金所持を証明しない。
- 通常の利用者保護操作はAUTH/CSRF/現在epochと、種別の資格・所持・承認を検証。直接APIも同じ。§5.4の目的限定capability/事業者署名/投票受付候補は別契約で、Cookieや通常署名を一律に要求しない。認証情報を票の公開入力に入れない。
- 候補本人の辞退は候補本人の真正署名、資格失効は認可発行者の因果/失効証明。運用者の理由だけで票を消さない。
- 初期資格は募集ごとの一つの共通発行機関/policy版へ固定する。複数issuer併用は機関横断の同一人排除を検証するまで不可。1人1票は募集/選挙ラウンド単位の使用済み印と秘密所持により検証し、複数メール/アカウント/カード/入金で増やさない。応援支援は投票資格へ転用しない。
- パネルの5人/3署名は初期案。単なる異なる鍵文字列ではなく、固定snapshot、外部一意性・独立性、利害排除、任期/補充、二重/矛盾署名を検証する。
- 参加者予算投票、検収、異議裁定、銀行実行を別権限にする。支払先・候補・関連者は自己承認できない。
- メール停止/削除・認証失効で過去票/使用済み印/既払い/個別権利を消さない。認証復旧を資格再発行にしない。

## 4. 永続化する論理モデル

各オブジェクトにschemaVersion/ruleVersion/environmentId。識別子は募集/使途/ラウンド単位でscopeを明示する。事件を統合しても募集・当事者・資金・委任・証拠を自動合算しない。

| 集合/オブジェクト | 主要項目・拘束 | 正本/公開境界 |
|---|---|---|
| EventProposal/ReviewRound | proposalId/version/hash、公開項目、候補集合/モデル/catalog版、roundId、固定panel、単一結論署名、元期限 | 基盤は版/hash/決定/参照の検証記録。本文は訂正・削除可能な配信、審査前ミラー複製なし |
| Catalog/FinalizationWait | catalogVersion/root、finalEventId、firstReadyAt、proposalId、signedVersion、diffHash、reconciliationStartedAt、signatureExpiresAt、元deadline | 同じ合意基盤でCAS/順位/期限。ミラーは投影 |
| Recruitment/RuleManifest | eventIdとは別ID、対象/支援区分/使途、契約主体、条件/費用/リスク/全期限、ルールhash | 集金前に固定。未承認案の既定値で実受付不可 |
| Eligibility/VoterSnapshot | 発行者/policy、募集scope、秘密commitment、有効/失効、集合commitment/N | 本人/入金対応表は外部。使用済み印はラウンド別 |
| Election/CandidateEvent/Hold | electionId、候補条件hash、selectedCandidateId、FINAL決定ref、対象候補/参加者/証拠、hold理由/版 | FINALと過去票は不変。別イベントとして追記 |
| Budget/Contract/Disbursement | 使途、承認、受取先opaque ref、段階、額、検収/裁定/異議、予約/許可期限、実行キー | 公開決定と私的銀行証明を分離。外部契約/銀行強制 |
| PaymentEvent/RightsLedger | providerEventId/hash、transactionVersion/previousHash、募集/私的ref、SETTLED/取消等の累計額、外部owner集約、rightsVersion | 最小外部因果証明。私的、欠番/逆順は照合待ち |
| Liability/CashProof | liabilityId、feeDue/legalDebt/reserve/refundPayable、予約対応、signedCash/版、不足・補填債権・実収 | 同一円の債務/予約二重計上なし。単なる保証はcashでない |
| RefundBatch | 固定集合/commitment、w/W、cap、F、基準版、固定tie順、裁定署名、原allocations | 全量一括予約。確定後immutable、新原資は新batch |
| RefundInstruction/ExecutionIntent | 固定銀行キー、original/completed/offset/reserved、instructionVersion/executionVersion、原intent bytes/hash、元署名/操作キー、retry履歴 | 旧版/旧payloadを上書きしない。金額/owner refは私的 |
| OffsetEntry/BankTerminalProof | 取消イベント×固定キー×相殺前版、額、前後根、旧実行版fence、確定/永久未送金額 | 署名付き追記。UNKNOWNは解放しない |
| OperationReceipt/ProofInbox | scope付き操作キー、payloadHash、決定proof/ref、nonce/nullifier消費、外部因果cursor/保留理由 | 同キー異payload拒否。権威あるreceiptが正本、DBキャッシュだけで成功にしない |
| GateDecision/DeploymentManifest | gate/evidence hash、対象ルール/実装/事業者/環境版、承認者、期限/失効、3/5署名 | 合意基盤で検証。環境変数や管理DB編集を解除にしない |

選任/カタログの確定と、関連operation receipt/nonce/nullifier消費は同じ権威ある更新に含める。私的資金の予約/相殺/指示版とreceiptは外部強制側の同一原子的更新に含める。API側キャッシュ書込の失敗は、確定済み外部操作の失敗/再実行根拠にしない。

## 5. 操作エンベロープとAPI

URL案であり採用未承認。参照仕様第12.2〜12.3節の論理操作が先で、特定DB/HTTP設計を正典へ昇格しない。

### 5.1 通常の利用者保護操作の共通検証

以下は通常の利用者保護操作に適用する。目的限定capability/事業者署名と、VOTE-03のCookieに依存しない資格所持証明による投票受付候補は§5.4の別契約として扱い、通常AUTH/CSRF/利用者署名を一律には課さない。例外は通常API全体の認証を外す根拠にならない。

1. 閉じた入力schema：未知版/field/operation/environment拒否。JPYは整数1円・安全整数範囲、合計/中間演算もoverflow拒否。`mode:'demo'`、`verified:true`、文字列proof、任意signer配列を認可入力にしない。
2. AUTH/CSRFと現在epoch、本人操作の署名/所持、対象scopeと操作種別の役割を検証。ネットワーク認証と本人/所持/定足数は別。
3. 署名対象は参照仕様第12.2節の共通エンベロープ全項目：`{domainTag,environmentId,consensusId,schemaVersion,ruleVersion,operationName,targetId,targetVersion,payloadHash,expectedStateRoot,nonce,idempotencyKey,issuedAt,expiresAt,signerProof}`。全項目を署名し、所持証明の公開入力も同じpayload/選択に結合する。RFC 8785相当の固定正規化でUTF-8化し、未知/重複キー・浮動小数/非整数JPYを拒否、文字列規則をschemaで固定。日時はUTC整数秒、区間は`[opensAt,closesAt)`、最終化済み基盤時刻で判定する。hash/署名アルゴリズム・ドメイン分離・時刻許容差・最終性は監査前未選定。署名済みbytesを再編集しない。
4. 認可issuer/key/policy、失効、期限、固定panel/独立性、同一結論、最新証明/根を検証。外部署名でも私的事実の真実性は残余信頼で、独立会計照合を要する。
5. 既存receipt同キー同payloadなら同じ元決定を返し、異payloadなら拒否。私的結果は現在の閲覧/所持認可も必要。権威ある受理/更新前の検証拒否（REJECTED）ではnonce/新決定receipt/業務ID/予約/現金を消費しない。受理後の銀行FAILED/UNKNOWNは別で、原許可・receipt・一意消費・予約・試行履歴を保存する。同じenvelopeの再送は新予約/投票/送金にせず、受理済みreceiptを銀行COMPLETEDへ読み替えない。再試行は§5.3に従う。
6. 必要ゲートと現在根/因果版/CASを検証し、権威ある主体で更新＋一意消費＋receiptを確定。API受付、outbox送出、HTTP200/202は確定証明ではない。

型ブランド`VerifiedProof`だけでは安全性は成立しない。サーバーの実Verifierだけが検証結果を生成し、外部DTOの自己申告と区別する。client入力や投影DBから作れる`verified`フラグを銀行へ渡さない。

### 5.2 API群の案

参照IDを含む私的照会はPOST body内とし、認可した本人/会計担当へ最小結果だけ返す。推測困難なIDを認可の代替にしない。公開データは独立ミラーでも署名/最終性を検証する。

| API案/論理操作 | 追加署名・条件 | 確定するもの |
|---|---|---|
| POST `/api/v1/proposals/submit` / submitProposal | 公開schema、端末AI/評価済model/candidate/catalog版、提出者署名 | 審査開始可否。AIの実行申告を暗号実行証明と呼ばない |
| POST `/api/v1/reviews/decide` / signReviewDecision | 固定panel、round/payload/candidates/期限/単一結論 | 署名記録。単独1票でFINAL不可 |
| POST `/api/v1/catalog/reconcile` / reconcileProposal | 全final差分、元の同じ5人全体の比較/その3人の最新版専用署名、関連/未分類の根拠 | 待機/保留/新審査。分類radio値を証明にしない |
| POST `/api/v1/catalog/finalize` / finalizeEvent | 最新root/catalog版、異議終了、署名/期限、ready順位 | 同一合意基盤のCASでeventId/新catalog版 |
| POST `/api/v1/elections/candidate-event` | 本人辞退または認可登録の失効、candidateId/条件版/因果根 | 対象候補履歴/必要hold。敗者辞退で勝者を停止しない |
| POST `/api/v1/elections/objections` | electionId、根拠/理由/不正証明、独立受理判断 | 有効性異議/未解決hold。元FINALの置換でない |
| POST `/api/v1/finance/disbursements/authorize` | 資格者予算/契約、検収、異議/裁定、選任の最新条件、額/版/原資 | 外部正本の該当予約。銀行commitでも再照合 |
| POST `/api/v1/finance/disbursements/execute` / executeBankTransfer | 既存の支出許可/同キー、最新選任条件/保留/予約/額/受取先/原資/期限を銀行確定点で共同照合 | 外部指示/commit証明。通常支出の原許可を新keyで二重消費しない |
| POST `/api/v1/finance/refund-batches/finalize` | 外部owner集約、固定w/cap/F/全版、当該既存裁定パネル3/5、一括原子的予約 | 不変batch/全instructions |
| POST `/api/v1/finance/refunds/offset` | 取消因果証明、当該既存裁定パネル3/5、未送金終端/fence、最新権利/指示/root CAS | 相殺追記/同債務減額/旧版失効。cash/既払い不変 |
| POST `/api/v1/finance/refunds/execute` | 原intent/固定キー、最新holder/rights/予約/指示版/原資、外部強制 | 外部操作ref。返金済みには銀行完了証明を要する |
| POST `/api/v1/provider-evidence` / consumePaymentEvent・bank reconciliation | 認可事業者の目的別署名、最小schema/因果版、環境/操作/対象結合 | 検証済み累計差分/保留。生Webhook転送は禁止 |
| POST `/api/v1/private/query-operation` | 現在AUTH＋該当権利所持/独立会計の正当な閲覧権限 | 私的操作/部分完了/UNKNOWN/不足と最終検証時点 |
| 通知/認証API（別領域） | 方式別AUTH又は目的限定確認/停止/削除token、購読抑止。例外へ通常Cookie/署名を一律に要求しない | 個人の通知/鍵操作だけ。票/会計に影響させない |

投票・資格登録、予算/検収等の全体APIは参照仕様第12.3節を継承し、上表は指摘1〜3の接続面を具体化したもの。元決済返品はPAY-04の別operation/schemaで、元入金/元権利/原資/固定返品キーだけを照合し、選任/検収を前提にしない。通常支出を返金/返品と偽装する入力は拒否する。

### 5.3 原intentと現在実行context

固定銀行キーは `(recruitmentId,batchId,privateRefundOwnerRef)`、実行許可の操作キーは `(固定銀行キー,executeRefund,executionVersion)`。原intentは対象/額/受取先opaque ref/実行版/原署名payload/許可期限等をimmutable保存する。

初回操作を正本で一度だけ受理し、その原許可を参照する現在実行contextとして、最新rights/transaction/予約/instruction/root、現在の所持証明、銀行challenge/fence、必要GateDecisionを別に検証する。contextは原intent hash/銀行キー/実行版へ真正に結合し、どちらかだけ有効な組合せを拒否する。contextの正規化・署名・bank認可仕様は採用事業者との未決契約である。

同一envelopeの再POSTは元決定を返すだけで、一般mutationを再適用しない。FAILED後の再試行は、正本に存在する同じ原許可を外部強制エンジンが再検証して行う別の実行試行。新しい輸送request ID/試行contextは新しい送金許可や額ではない。原intentの署名/期限を変えず、原許可の有効期間と承認済みretry期間/回数の交差内だけ許す。照合記録だけでexecutionVersionを増やさない。

UNKNOWNでは再試行しない。旧版の将来不実行/fence、裁定相殺、原子的CASが成立したときだけ新残額実行版/別操作キーへ。元keyの24時間等の保持期限が切れたから新keyで送ることはしない。期限/回数後も予約と権利を維持し外部請求へ。返金先/権利移転は外部の所持・署名手続を要し、同版intentの書換やメールによる受取先変更は許さない。

### 5.4 非通常経路

- 認可事業者の証明受信は人のログイン/本人署名ではなく、目的別事業者署名で検証する。ネットワーク接続認証だけで未検証の中身を確定しない。
- MAIL-06 stopOnlyは限定tokenで停止のみ。Basic/ログイン/Cookie/通常CSRF/通常操作署名を要求しない。GET停止/再開、宛先取得、資格復旧不可。将来proxy例外を設ける場合はmethod/path/purposeを限定し、通常APIへ横展開しない。現在のproxyは本作業では変更しない。
- confirmEmail/delete capabilityは目的・世代・期限・単回性を検証し、通知確認/削除だけを許す。通常の利用者署名/AUTH/CSRFを一律には要求しない。配信状態確認も事業者署名等の目的別認可で、利用者Cookieに依存させない。
- VOTE-03は通知登録/認証Cookieに依存せず資格所持証明で投票を受け付ける候補方式をG-02で評価する。資格/署名/操作scope・使用済み印の検証は必要で、この未決方式を本書でCookie必須へ変更しない。通常の私的照会/アカウント操作とは別の認可契約。
- token URL/署名/本文をアプリ、GCP/CDN/監査/エラーログへ残さないことの実証前に通知本番化しない。

## 6. 原子性・因果順序・資金

### 6.1 外部の直列化点

不可逆銀行commitと同じ共同順序で、当該募集/使途の最新権利・外部失効・candidate条件/hold、予約/現金、指示/実行版/旧版fence、同じ円の消費を検証する。外部で失効が成立した時点を、後着Webhookの受信順で置き換えない。

`prepare/reserve → signed commit-or-abort + fence` は候補プロトコル名であり、アプリ実装だけで成立する分散transactionではない。参加主体、障害時の共同整合、確定/失効が「先」の定義、分断時の拒否、復旧/キー再発行時のfenceを契約・技術証拠で決める。単なる短いTTL、最後のHTTP照会、内部ロック、投影の最新読取では代替不可。

| 前提種別 | 銀行確定点で要する条件 |
|---|---|
| 通常支出 | 最新selectedCandidateId/条件が有効、必要holdなし、予算/契約/検収/裁定/異議/額/受取先/予約/原資/期限の同版一致 |
| 固定返金 | 固定batch/原割当/累計完了・相殺、外部所持/最新権利/予約/root/実行版、同銀行キー版横断総額/原資。選任/契約/検収は追加前提にしない |
| 予約相殺 | 取消因果署名、既存裁定3/5、対象旧版の未送金・永久不実行証明、CAS、追記/債務減額/旧版fenceを同時確定 |
| 元決済返品 | 対象入金の因果版/元権利、返品台帳/予約/残額/原資、元決済先、固定返品キー、取消/返金との重複消費禁止 |

API、管理画面、手動、サポート、昇格/鍵再発行、受取先更新、緊急/例外、事業者自身に同じ種別条件を強制。名義人の任意引出やowner overrideは不可。法令・銀行独自凍結等の残余外部権限と倒産請求を隠さず、未確定ならG-03/G-05未達。

### 6.2 固定バッチと会計

- PAY-07の外部本人集約により複数入金で端数順位を増やさない。固定wは未取消拠出、capは有効拠出−確定非返還費用−完了返金−未完了予約（下限0）。UNKNOWNも予約控除する。
- `F <= min(refundAvailable, Σcap)`。w/cap/F/基準版/順位/裁定署名を固定し、cap>0かつw>0の対象から始める。残原資f・残重みWの理想額を整数交差積で比較し、cap超過者全員へcapを割当て同時除外、f/Wを再計算することを超過者がなくなるまで繰り返す。その後floor、端数降順/固定参照tie順の1円配分を行う。W=0、原資/版不明・不足は拒否する。中間交差積にBigInt等を用い、`Σallocation=F`、`0<=allocation<=cap`を検証。原batch/累計既払いを再按分しない。
- `obligations`は同一liabilityIdの重複を除く債務/準備金/予約/refundPayable/未払手数料。`refundAvailable=max(0,cash-obligations)`。現金は銀行署名照合と一致させる。
- 取消は最新因果版/前hash/providerEventIdで一度だけ。欠番/順序不明は権利と新操作を照合待ちへ。古いSETTLEDで取消を復活させない。
- 相殺はcash/既払いを変えず必要未送金額だけを追記し、`original=completed+offset+reservedRemaining`を維持。同時に同じrefundPayable/予約を二度消さない。
- 借越/立替債務/補填債権/損失は別記録。非現金請求権をcashへ足さず、補填の実収は銀行/保管の証明が来た時のみ。デモ`externalAdvance`の仮定補填は本番へ移植しない。
- 原資不足では新支出/新batch/既予約自動実行を停止。権利を削除せず、他募集や新出資から無断補填しない。保証範囲/準備金/取消最長期間/負担主体/請求不能時/倒産を募集前に法務確認する。

### 6.3 部分完了・終端・復旧

50円の指示で30円確定・20円UNKNOWNなら、差分30円だけをcash/予約/完了額へ記録し20円を保全する。累計completedは真正署名と単調性で差分適用し、重複receiptでcashを二度減らさない。

相殺/新版移行に必要な終端証明は、環境/保管主体/固定銀行キー/旧実行版/原intent hash/外部順序位置、確定額、未送金額に結合し、キュー・手動・API・自動再試行・復元再生でも旧残額を将来実行不能にするfenceの証拠を含む。単に「今まだ送っていない」「FAILED」「タイムアウト」は不十分。部分完了済みの額は相殺不可。

復元時は外部正本の根/因果履歴、receipt/取消/相殺/版横断累計、nonce/nullifier、未終端予約を再照合するまで新実行を止める。キャッシュが空になっても「未使用/予約なし」と解釈しない。銀行commit後の応答消失は照合対象で、新操作IDでの再払いにしない。

## 7. カタログ/選任の確定

### カタログ

AI候補は端末内検索、評価証拠を持つモデル/公開索引とし、外部推論送信・人だけへの本番fallbackをしない。端末実行申告の保証範囲はG-04の未決事項。

無関係再照合は元の同じ初回5人のパネル全体が差分を比較し、その5人中3人の専用再署名を要求する。別の独立3人を後から選んで代用しない（CASE-09、人数は未承認案）。

CAS、署名/差分、待機順位、期限は同じ合意基盤で検証。元firstReadyAt/proposalId順を保持し、先行未準備なら他readyを処理できるが順位/期限は延長しない。無関係競合回数では失効せず、全最新差分と変更なしpayloadに元の同じ5人中3人の専用署名。未分類は保留、重複/候補や比較変更は新提案/新round/全署名/異議窓口へ戻る。

再照合開始からの48時間、成功専用署名からの48時間、元暫定承認からの12日を区別。同未完了期間のstartは固定、成功期間だけ終了する。現在専用署名の期限は次期間でも保持し、切れた署名を再署名で復活させない。原提案期限もresetしない。バックエンド候補の時刻規約は前工程同様`now < expiresAt`（一致から失効）。採用はルール承認待ち。時計は権威ある合意基盤の検証可能な時間を使い、ブラウザー/メール到着/workerのDate.nowを起算点にしない。

### 選任・投票rootとscope

開始前に募集ごとの共通issuer/issuerPolicyVersionと、唯一の最終化済み資格rootVersion/rootHash、N、候補条件、ruleVersion/全期限を固定する。INITIAL/RUNOFFの双方は同じroot/Nを受理し、開始後のroot差替え、新資格/秘密、発行者/policy切替を拒否する。固定rootは集合所属、現在の失効は別の有効性判断であり、失効時にroot/分母を縮めない。

scopeは参照仕様どおり`H(domainTag,environmentId,consensusId,recruitmentId,electionId,roundId,ruleVersion)`。rootVersion/候補/authId/額をscopeへ含めず、所持証明へscope/rootHash/候補集合hash/選択/操作期限を結合する。同scopeのnullifierを状態更新と一度だけ消費し、別候補/アカウント/root/リレイヤーによる増票を拒否。INITIAL→RUNOFFは別roundの各1票。選挙IDは環境/基盤をまたいで再使用しない。途中の認証復旧/メール所持で新秘密を認めない。

FINALのselectedCandidateId/候補条件hashは変更しない。イベント対象が勝者か敗者か、参加者条件喪失か、有効性異議かを分ける。勝者/参加者の条件喪失、受理済み未解決の有効性異議は新契約/支出を保留。敗者の単なる結果後辞退は候補履歴のみ。銀行commit先なら既払い/FINALは保持し、その後の新支出を止める。既存指示の真正照合は継続できる。

通常の異議期限と、FINAL後の新証拠による独立訂正/保留判断を区別。元期限内以外の再選挙、投票削除による分母調整、メール/運用者による代理投票/タイブレークはしない。

## 8. ゲート・状態・画面

Gate解除/再停止はユーザーの初期値承認、独立領域評価者の証拠、評議会3/5、解除前7日公開、対象版固定に従う（第13.1節、数値は未承認案）。GateDecisionは対象版/環境/事業者/証拠/評議会/期限・失効を検証する。案件初回/別再審査、元パネル再照合、検収/別裁定、参加者予算投票、評議会をoperation別の固定snapshot/role scopeへ結合し、別集合の3署名を混用しない。返金バッチ/相殺は当該既存裁定パネル3/5を要する。ルール新版は新募集にのみ適用し、既存資金/票を改変しない。何か一つの`G03=true`やデモproofを本番許可にしない。一般state CASと、ゲート/資格/銀行の最新性は別に検証する。

| 種類 | ゲート未達/失効時 |
|---|---|
| 新登録/集金/選任/新承認/新銀行実行 | 関連するGを満たすまで拒否。要件未確定はCLOSED/UNKNOWNとして扱う |
| 既に確定した決定/既払い | 後から未達になっても改変しない |
| 既指示・取消・失効の真正証拠の受信/照合 | 鍵/真正性/因果が検証できる範囲で継続し、過去を保全。検証不能なら隔離/UNKNOWN、成功を推測しない |
| 既債務/未請求返金 | 権利と予約を保全し、独立会計/外部請求導線を維持。G未達を返金権利失効にしない。新銀行実行は所定条件なしで許さない |
| 個人通知の停止/削除 | 既発行の目的限定capabilityの範囲で維持。新登録/送信停止と混同しない。復元抑止不明はRESTORE_BLOCKED |

UIは「依頼受付」「権威ある確定」「銀行処理中」「結果不明」「部分完了」「不足」「外部請求」を区別し、確認した根/版/時刻を表示する。受信・外部ジョブ投入を返金済み/FINALと表示しない。本人の私的原票公開で検証可能性を補わない。

本番からは固定候補、timer成功、デモ認証省略、証拠file選択/アップロードを除去する。旧localStorage下書き/参加情報を無断でサーバーへ移行しない。公開案件の確定は募集/資金/委任の自動統合ではない。
